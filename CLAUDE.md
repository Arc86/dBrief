# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

dBrief is a macOS menu bar app (SwiftUI `MenuBarExtra`) for recording microphone and system audio, then automatically transcribing and analyzing recordings with AI. It generates summaries, action items, tags, and sentiment, and can export results to Markdown notes, Obsidian vaults, and eight integration destinations. Built as a Swift Package Manager executable (not an Xcode project).

## Build Commands

- **Build**: `swift build` (debug) or `swift build -c release`
- **Build app bundle**: `make app` (builds release `--arch arm64`, assembles `dBrief.app/` with Info.plist, icons, Metal shaders, and a bundled static `ffmpeg` in `Contents/MacOS/`, then signs it with a stable self-signed cert)
- **Run**: `swift run` or `make run` (builds and launches the app bundle)
- **Beta channel**: `make beta` (or `make run-beta` to build + launch) assembles a fully separate **`dBrief-Beta.app`** — bundle id `com.dbrief.app.beta`, display name "dBrief Beta", signed with its own stable `dBrief Beta Self-Signed` cert, Sparkle feed stripped. macOS treats it as a distinct app, so it gets **independent TCC permission grants** (mic, Screen Recording, Calendar…), UserDefaults, Application Support, and Keychain — a test build never collides with the installed production build's permissions or data. All identity-scoped storage is namespaced under the runtime bundle id via `AppSupportPaths` (`Utilities/AppSupportPaths.swift`), which the ML helper inherits through `--support-base`; the shared FluidAudio model cache (`~/Library/Application Support/FluidAudio/Models`) is intentionally left shared (identical weights, no user data). The `beta`/`run-beta` targets override `BUNDLE_ID`/`DISPLAY_NAME`/`BUNDLE_DIR_NAME`/`SIGNING_CERT_NAME` in the Makefile; release defaults leave `make app`/`dmg`/`notarize` unchanged.
- **Sign**: `make sign` (`codesign --deep` with a stable self-signed identity `dBrief Self-Signed`, auto-created/reused by `scripts/ensure-signing-cert.sh` so macOS TCC permissions — Screen Recording, etc. — survive app updates instead of resetting each release; falls back to ad-hoc `-` if the cert can't be created. Override `CODESIGN_IDENTITY=-` for pure ad-hoc, or with a Developer ID if you enroll)
- **Build DMG**: `make dmg` (builds the app, then a compressed `dBrief-<version>.dmg` with a drag-to-Applications symlink, for GitHub Releases)
- **Notarize** (the standard public-release path, requires Apple Developer Program): `make notarize CODESIGN_IDENTITY="Developer ID Application: …" NOTARY_PROFILE=<profile>` — hardened-signs with `packaging/dBrief.entitlements`, notarizes + staples the app and DMG (removes the Gatekeeper prompt). Used for the released DMG since v1.3.1; `make app`/`make sign` still default to the self-signed cert for local dev and Homebrew-from-source. See [RELEASING.md](RELEASING.md)
- **Clean**: `make clean` or `swift package clean`
- **Run tests**: `swift test`
- **Summary editor bundle**: after changing `web/markdown-editor/` (or bumping `@milkdown/*`), run `npm ci && npm test && npm run build` there and commit the regenerated `Sources/dBrief/Resources/MarkdownEditor/` files.

The app version is the single source of truth in `Sources/dBrief/Resources/Info.plist` (`CFBundleShortVersionString`); the Makefile, About screen, and `UpdateService` all read it. Cutting a public release (version bump → `make notarize` → Sparkle appcast → GitHub tag → Homebrew tap) is documented in [RELEASING.md](RELEASING.md). The released DMG is **Developer ID-signed and notarized** (since v1.3.1, so it opens with no Gatekeeper prompt), Apple Silicon only; Homebrew-from-source and local dev builds remain self-signed (stable cert, for TCC permission persistence).

## Architecture

### App Lifecycle & Dependency Wiring

`DBriefApp` (`Sources/dBrief/App/DBriefApp.swift`) is the `@main` entry point. It creates a single `AppContext` instance that owns all shared state and services. Dependencies are passed to SwiftUI views via `.environment()`. The app runs as `LSUIElement` (no dock icon by default), presenting a `MenuBarExtra` window and a separate settings `WindowGroup`.

### Core Object Graph

- **AppContext** — root object, creates and wires everything at launch; owns all services below
- **AppState** (`@Observable`) — **capture-only** recording state machine (`idle → recording → paused`), plus a decoupled background `processingJob` (`ProcessingJob`), processing step progress, current recording data, call detection state. Capture and processing are independent so a **new recording can start while a previous one is still processing** (see [Concurrent capture + processing](#concurrent-capture--processing-record-while-processing))
- **AppSettings** (`@Observable`) — all user preferences persisted via `UserDefaults` with `didSet` observers; folder URLs use security-scoped bookmarks; integration tokens stored in Keychain via `KeychainHelper`. Split across extension files: `AppSettings+EffectiveSettings.swift` (profile-resolved computed properties), `AppSettings+Profiles.swift` (profile CRUD, import/export, factories), `AppSettings+Persistence.swift` (bookmark/endpoint/integration/profile persistence helpers)
- **RecordingManager** — orchestrates the full record → finalize → transcribe → AI → markdown → integration dispatch pipeline

### Concurrent Capture + Processing (record-while-processing)

Capture and post-recording processing are decoupled so a **new recording can start while a previous one is still transcribing/analyzing** (the Record button and hotkey stay live during processing). `AppState.recordingState` is **capture-only** (`idle`/`recording`/`paused`); background processing is tracked separately by `AppState.processingJob` (a `ProcessingJob` — `Models/ProcessingJob.swift` — owning only what conflicts with a concurrent capture: its recording, a cancellable task, its queue sidecar, and its progressive segments). `processingSteps`/`liveInferenceText` stay `AppState` singletons since only **one job runs at a time** (the ML helper serializes GPU work anyway).

- **Overflow queueing**: a recording finished mid-processing auto-enqueues as `QueueItem.autoQueued`; the queue **auto-drains one-at-a-time** when the current job finishes. Manual "Process Queue" still drains user-deferred items too.
- **Cancellation / review**: confirm-first speaker review resumes inside the job's task; `cancelProcessing` cancels the task, tears down any pending review, awaits the task's unwind before draining (no two concurrent pipelines), and skips integration dispatch on cancellation.
- **Idle gating**: `RecordingManager.isIdle`/`canDownloadModels` require **no active job** (distinct from `AppState.isIdle`, which is capture-only and drives the Record button).
- **UI isolation**: the menu's Record button coexists with the processing banner; the transcript browser shows **dual "In Progress" pins** (capture + job); the transcript window and chat isolate live/progressive segments per recording so a concurrent capture can't leak into a processing recording's view.

### Audio Capture (`Audio/`)

`AudioCaptureManager` handles two recording modes:
- **Mixed mode** (system audio + mic): uses `ScreenCaptureKit` for system audio via `SystemAudioCapture`; the mic is a `MicSource` (below). The two sources are captured to **separate per-track CAF/LPCM files** (`*.system.caf`, `*.mic.caf`) and mixed at finalization, not in real time.
- **Mic-only mode**: when screen recording permission is denied (no system CAF is written).

**Important concurrency note**: Audio callbacks must be created with `nonisolated static` methods to avoid inheriting `@MainActor` isolation, which would crash on the real-time audio thread. See `MicSourceFactory.makeHandler(sink:)` and `makeSystemHandler`.

**Microphone sources and device switching** (`Audio/MicSource.swift`, `Audio/MicReconfigurePlanner.swift`, `Sources/NativeMic/`): a device switch never re-points a running capture — the old `MicSource` is stopped and a new one built for the new plan. The pure, unit-tested `MicReconfigurePlanner.decide(...)` (`MicReconfigurePlannerTests`) returns a `MicSourcePlan` (concrete device UID + `MicBackend` + VPIO): a pinned device stays while present, a **gone** pinned device falls back to the system default, "System Default" follows the new default, and VPIO is `aecSetting && outputHasEchoPath && micOnly`. **Backend rule:** the macOS default input uses `EngineMicSource` (a **fresh** `AVAudioEngine` per plan, never binding a device); any other device uses `CaptureSessionMicSource` (`AVCaptureSession` on the exact UID). Writing `kAudioOutputUnitProperty_CurrentDevice` on AVAudioEngine's input is **forbidden** — on current macOS it yields zero callbacks or a stale-format `NSException` on switches (`docs/diagnostics/2026-09-20-audio-switching-review.md`, 2026-09-21 capture-session probe). VPIO exists only on the engine backend. All AVFAudio/AVCaptureSession calls go through the typed Objective-C wrappers in the `NativeMic` target (`NativeMicEngine`, `NativeMicCaptureSession`), so an `NSException` becomes a Swift error instead of unwinding Swift frames. Stopped engines are retained briefly (`EngineMicSource.retired`) because queued AVFAudio route callbacks race `AVAudioEngine.dealloc`.
- **One continuous track**: every source writes through a `MicCaptureSink`, which creates a `MicFormatConverter` from its first buffer when the device's format differs from the track on disk, and pads the outage between two sources with silence via the shared `MicTimeline` (host-time based; reset on pause, since both tracks stop) so the mic track stays aligned with system audio (`MicSourceSwapTests`).
- **Callers**: manual `switchMicrophoneDevice(to:)` (the mic menu via `RecordingManager.switchInputDevice(to:)`; the chosen device is treated as present so an enumeration race can't trigger the gone→default fallback) and automatic — CoreAudio listeners on default input, device list and default output, plus the engine's configuration-change notification — funnel into one debounced (400 ms) `scheduleReconfigure()`. `resumeRecording` reconciles before starting, so a device changed during a pause is never restarted.
- **Health**: the meter tick checks delivered buffers (`MicHealth`, 4 s). A source that never delivers gets one alternative via `MicReconfigurePlanner.fallback` (engine → capture session on the same device; pinned session → default engine); a source that stops delivering, or stops itself, is rebuilt at most 3 times before a persistent "Microphone isn't delivering audio" note. A failed start tries the fallback, then restores the previous source and rethrows.

The recording mode is chosen automatically by permission (mixed when Screen Recording is granted, mic-only otherwise) — there is no user-facing source toggle. Capture is per-track CAF/LPCM; the finalized master is **M4A/AAC (~96 kbps, 48 kHz stereo)**. The audio source toggle (mic vs. mixed) is not exposed in Settings; the **Settings → Recording** tab exposes input device, an acoustic echo cancellation toggle (`acousticEchoCancellation`), and a read-only Audio Quality summary (in its Advanced card).

### Recording Finalization (`Services/RecordingFinalizer.swift`)

`finalize(tracks:…)` takes the separate captured CAF tracks (`CapturedTracks`) and, after recording stops:
1. Normalizes meeting title (sanitizes special chars)
2. Creates dated folder structure (`Recordings/YYYY/MM`)
3. Merges + transcodes the per-track CAFs to an M4A/AAC master via ffmpeg, applying DSP per track (mic: 80 Hz HPF, sidechain duck vs. system, -16 LUFS loudnorm; system: 40 Hz HPF, 12 kHz LPF; mix: `amix` normalize). Acoustic echo cancellation (`echoSuppressionEnabled`) ducks mic against the system reference.

**Echo-cancellation route gating**: echo cancellation (real-time Voice Processing in mic-only mode, offline sidechain duck in mixed mode) only helps when speaker output bleeds into the mic. On headphones/earphones (incl. AirPods) or any non-built-in output there's no echo path, and Voice Processing needlessly ducks output + applies AGC — the audible "volume gets much lower on earphones" symptom. `AudioOutputRoute.echoPathExists(transportType:dataSource:)` (pure, unit-tested in `AudioOutputRouteTests`) returns `true` only for built-in speakers (`kAudioDeviceTransportTypeBuiltIn`, and not the `'hdpn'` headphone data source); `AudioOutputRoute.currentOutputHasEchoPath()` wraps the CoreAudio query (default output device → transport type + data source), defaulting to `true` when undeterminable. **Two consumers with different lifetimes:** (1) the **live VPIO** path — `RecordingManager` passes the *raw* `acousticEchoCancellation` setting into capture, and `AudioCaptureManager` re-gates dynamically on the output route (the `DefaultOutputDeviceMonitor` → `scheduleReconfigure` path toggles `setVoiceProcessingEnabled` mid-recording when you move between speakers and headphones; toggling requires `engine.stop()` and shifts the node format, so the converting tap engages automatically). (2) the **offline mixed-mode sidechain duck** — `RecordingManager.startRecording` still computes `echoCancellationActive = setting && currentOutputHasEchoPath()` once and freezes it on the session-only `Recording.echoSuppressionApplied`, because that ffmpeg filter is all-or-nothing over the whole mic track.
4. Auto-segments files >30 minutes into 30-minute chunks (`_partNN.m4a`) — each chunk is transcribed and (if diarization is on) diarized independently, then the per-part speakers are unified back into one global identity space (see Speaker Diarization → **Cross-part speaker reconciliation**)
5. Writes JSON metadata sidecar (`RecordingMetadataPayload`) with duration, warnings, and segment file names
6. If ffmpeg is unavailable (or merge fails), falls back to promoting a raw CAF track to the master path (no AAC encode); segmentation is then skipped

Final file naming: `YYYY-MM-DD_HHMM_[meeting-title].m4a` — the `[meeting-title]` segment is the **draft** title at finalization (the audio file is never renamed later). The AI-generated title produced during post-processing is instead written back into the metadata sidecar's optional `generatedTitle` field by `RecordingManager.persistGeneratedTitle(for:)` (after Markdown generation, both the normal and retry-AI paths). The transcript browser (`RecordingBrowserItem.title`) and the menu-bar history (`RecordingHistoryView`) **prefer `generatedTitle`** over the filename-derived title, so a reopened recording shows the AI title rather than the stale draft (#71). Old sidecars without the field decode leniently and fall back to the filename.

**User-provided titles are never overwritten**: when the user types/keeps a custom meeting title in `PostRecordingSheet` (detected via `isCustomTitle` — not the default fallback), the session-only `Recording.titleWasUserProvided` flag is set, and `RecordingManager.shouldGenerateTitle(for:)` gates every title path (`applyGeneratedTitle` for the unified engines' inline `title_concept`, and the separate `aiService.generateTitle` remote step) so AI titling is suppressed. The flag rides through the processing queue on `QueueItem.titleWasUserProvided` (decoded leniently, defaults `false` for old queue files), so a queued recording analyzed later still respects the typed title.

### Transcription Engines (`Services/`)

Four transcription backends selected via `AppSettings.transcriptionEngine`:

| Engine | Class | Backend |
|--------|-------|---------|
| Apple Speech | `AppleSpeechAnalyzerService` (macOS 26+) / `LocalTranscriptionService` (older) | Auto-selects per machine — one "Apple Speech" engine, no extra picker entry. macOS 26+ uses the modern `SpeechAnalyzer`/`SpeechTranscriber` (native `AVAudioFile` loading, word-level timestamps from the `audioTimeRange` run attribute, on-demand language-asset download via `AssetInventory` surfaced as a "Preparing language…" step); macOS 14–25, or a locale `SpeechTranscriber` doesn't support, falls back to the legacy `SFSpeechRecognizer`. Both share `OggOpusConverter` for `.ogg`/`.opus`→WAV via ffmpeg. The result→`TranscriptionResult` mapping is the pure, unit-tested `AppleSpeechResultMapper` in `dBriefWire`. |
| Local Whisper | `WhisperKitTranscriptionService` (via `LocalAIPluginService`) | On-device CoreML Whisper via the `WhisperKit` product of the `argmax-oss-swift` SDK (1.0.0). Loads audio natively (FLAC/WAV/M4A via AVFoundation — no ffmpeg needed). Uses WhisperKit's per-component compute defaults (mel→GPU, encoder→ANE, decoder→ANE). VAD chunking enabled. Downloads models to `AppSupport/dBrief/LocalAIPlugin/WhisperKit/`. Supports progressive segment streaming via `segmentDiscoveryCallback`. Dynamic model picker fetches available models from HuggingFace at runtime with memory estimates; falls back to curated offline list. Recommended default is the Sep-2024 large-v3 turbo (~632 MB, `WhisperModelInfo.recommendedModelID`). Optional SpeakerKit diarization. **Prompt-suppression guard**: the service still accepts an `initialPrompt` (fed to Whisper as `promptTokens`), but the **app no longer sends the custom vocabulary there** — an out-of-domain prompt makes Whisper emit *blank* text for most windows (segments keep time ranges but lose text — silent ~90% loss; vocabulary spelling now happens post-transcription, see Custom vocabulary). As defense-in-depth for any caller that does pass a prompt, `transcribe()` detects collapse (>50% of ≥4 segments empty after a prompted pass) and re-transcribes once **without** the prompt, keeping whichever pass has more non-empty text. |
| Parakeet TDT (Local) | `ParakeetTranscriptionService` (via `FluidAudio` framework) | On-device CoreML Parakeet TDT 0.6B: v2 (English), v3 (multilingual, default), **Ultra** (v3 post-trained for accuracy, same speed/size) or **Redux** (~220 MB, macOS 15+, several-minute first compile). `ParakeetModelInfo` (in `dBriefWire`) is the single catalog: `find()` resolves unknown or OS-unsupported variants to v3, so the picker (`LocalTranscriptionChoice.parakeet(_:)`/`parakeetVariant(_:)`), provenance label and helper (`ParakeetTranscriptionService.asrVersion(for:)`) always agree; download state is per variant (`isParakeetCached(variant:)`). FluidAudio's own logging is capped at `.warning` at helper startup (its debug lines can contain transcript text). Handles long files natively (no segmentation). Loads audio to 16 kHz mono `[Float]` via FluidAudio's `AudioConverter` and **appends ~1 s of trailing silence before ASR** so sentence-final punctuation isn't dropped at the sequence boundary (falls back to the file-based path for very long audio to preserve the disk-backed memory route). Emits **word-level segments** built from FluidAudio's `ASRResult.tokenTimings` (grouped on the `▁`/space SentencePiece boundary, split into segments on >1 s pauses; falls back to a single full-file segment when timings are absent). Does **not** support language selection. **Supports speaker diarization** via the shared SpeakerKit path (see Speaker Diarization). Reports download/load progress via the same `AsyncStream<LocalAIPluginState>` pattern as `LocalAIPluginService`. |
| Remote Endpoint | `TranscriptionService` | OpenAI-compatible `/v1/audio/transcriptions` (incl. **Groq Whisper** as a preset) and `whisper-asr-webservice` `/asr` (auto-detected via `Endpoint.isWhisperASR`); chunked upload for large files via `AudioChunker`. Also native **Deepgram** (`/v1/listen`, `Token` auth, word timestamps + `diarize`) and **ElevenLabs Scribe** (`/v1/speech-to-text`, `xi-api-key`) adapters selected by `Endpoint.provider`; their responses map to `TranscriptionResult` via the pure, unit-tested `CloudASRMappers`, and they bypass `AudioChunker` (long audio handled server-side). Providers are added via the curated `ProviderPresets` picker in Settings → Transcription. |

After transcription, **all** engines' results pass through the engine-agnostic `TranscriptCleanup` (in `dBriefWire`, called once in `RecordingManager.transcribeRecordingAudio`): it strips hallucination/markup noise (XML-ish tags, `[…]`/`{…}`/`*…*` non-speech annotations, leading/trailing dash runs) and normalizes whitespace always; removes filler words (um, uh, …) only when `AppSettings.removeFillerWords` is on (default off); and drops **ignored segments** — whole segments whose cleaned text exactly matches a known filler phrase — when `AppSettings.removeIgnoredSegments` is on (default **on**). The ignore set is `TranscriptCleanup.defaultIgnoredSegments` (curated Whisper/YouTube silence-hallucinations like "Thank you for watching", "Subscribe to the channel", "♪" — meeting-safe, excludes ambiguous bare words) unioned with `AppSettings.customIgnoredSegments` (user-added; "Reset to Defaults" clears them). Matching is whole-segment and case/punctuation-insensitive via `normalizeForIgnoreMatch`, so real speech merely *containing* a phrase is kept; when a segment is dropped the flat `text` is rebuilt from survivors. Resolved via `AppSettings.effectiveIgnoredSegments`. All configured in **Settings → Transcription → Cleanup**.

Four AI backends selected via `AppSettings.aiEngine`:

| Engine | Class | Backend |
|--------|-------|---------|
| Apple Intelligence | `LocalAIService` | On-device via `FoundationModels` framework. Guarded by `#if canImport(FoundationModels)` and `@available(macOS 26, *)`. Only available on Apple Silicon with macOS 26+. Config (`LocalCLIConfig`: command + timeout) is global, persisted as JSON in UserDefaults. |

AI tasks run sequentially after transcription: summary → action items → tags/sentiment → title generation → markdown export. All AI steps can be skipped via `AppSettings.aiProcessingEnabled = false`.

**Name-aware analysis (roster hints)**: before running any analysis path, `RecordingManager` builds a one-line **roster hint** from the known participants + calendar attendees via the pure `AnalysisRoster.hint(participants:attendees:)` (`Services/AnalysisRoster.swift`) — it dedupes case-insensitively and drops raw "Speaker N" placeholders, yielding e.g. `"People likely in this meeting: Alice, Bob."` or `nil`. The hint plus any calendar agenda is prepended to the transcript by `CalendarEvent.augment(prompt:with:roster:)` so the model spells names correctly and attributes statements accurately; speaker-substituted text comes from `TranscriptionResult.textForLLM(speakerNames:)`. The same roster is the eligibility gate in `VoiceIdentityResolver` (see Voice Library) — when non-empty, only on-roster people can win a confident voice match.

**Custom vocabulary** (`AppSettings.effectiveCustomVocabulary`, resolved from `customVocabulary: [String]`; `MeetingProfileOverrides.customVocabulary`; edited in the **Vocabulary** settings tab) is used in three places, but **not** as a Whisper/ASR decoder prompt — that path was removed because an out-of-domain (or even on-domain) prompt makes Whisper emit blank output for most windows, silently dropping the bulk of the transcript (OpenAI's own guidance recommends post-processing over prompt injection). The three uses are:
1. **Transcript spell-correction** (`TranscriptSpellingService`, run in `RecordingManager.transcribeRecordingAudio` after `TranscriptCleanup`): the active AI engine is asked for a bounded `[{from,to}]` correction list, which the pure, unit-tested `VocabularyCorrection.apply(_:vocabulary:to:)` (in `dBriefWire`) applies as validated whole-word, case-insensitive replacements — `to` must be one of the vocabulary terms, so the model can never drop or reformat transcript content. No-op when vocabulary is empty or no AI engine resolves. Local CLI routes to `chatFallbackEngine`; Apple Intelligence truncates the transcript for its ~4K window.
2. **AI analysis**: injected as a "spell these exactly" `### DOMAIN-SPECIFIC TERMS` block into every analysis path — `UnifiedInsightsPrompt.vocabularyBlock` / the `customVocabulary` params on `systemPrompt(…)` and `systemPromptForGuidedGeneration(…)` for the unified engines (threaded to the Gemma helper via `MLRequest.analyze`/`.analyzeStream`), and appended to the remote per-task system prompts in `RecordingManager.withVocabulary`.
Custom vocabulary is **not** sent as an ASR prompt to remote transcription endpoints either: the only remote consumers of `initialPrompt` are Whisper-family servers (OpenAI-compatible `prompt`, whisper-asr `initial_prompt`), which share the same fragility; Deepgram/ElevenLabs ignore it. So `RecordingManager` passes `initialPrompt: ""` for `.remoteEndpoint`, and the spell-correction post-step (use #1) covers remote transcripts too. The `initialPrompt` parameter remains on `TranscriptionService.transcribe` / `WhisperKitTranscriptionService.transcribe` as a dormant capability (defaults to empty / `nil`).

**Unified-result engines** (Apple Intelligence, Gemma local, and Local CLI) each produce a `LocalInsightsResult` in a single call (with an inline `title_concept`, so they all skip the separate title-generation step). Apple Intelligence does this via **guided generation** (`@Generable` schema, `FoundationModels`) using `UnifiedInsightsPrompt.systemPromptForGuidedGeneration`; Gemma local and Local CLI use a shared JSON prompt/schema via `UnifiedInsightsPrompt` (system + user prompt + transcript truncation, in `dBriefWire` so both the app and the helper can use it), with output parsed via `LocalInsightsDecoder.decodeAndNormalize`. **Custom analysis prompts reach the unified engines too**: the user's Summary / Action Items / Tags prompts (`effectiveSummaryPrompt`/`effectiveActionItemsPrompt`/`effectiveTagsPrompt`) are bundled into `UnifiedInsightsPrompt.InsightsGuidance` (each field optional; empty falls back to the built-in rule) and threaded to Gemma (`MLRequest.analyze`/`.analyzeStream` → `RecordingManager.effectiveInsightsGuidance`), Local CLI (`LocalCLIService`), and Apple Intelligence (`LocalAIService.analyzeTranscript(summaryGuidance:actionItemsGuidance:tagsGuidance:)`) — so on-device/CLI analysis honors the same per-field prompts the Remote Endpoint already used, while the unified prompt keeps ownership of the JSON envelope. **Local CLI cannot stream**, so the transcript chat window falls back to `AppSettings.chatFallbackEngine` (never `.localCLI`) when the active engine is Local CLI. The default fallback is `AIEngine.defaultOnDeviceFallback` — Apple Intelligence if available, otherwise local Gemma — so chat works without configuring a remote endpoint.

### Local AI Plugin System — Crash-Isolated Helper Process

All self-loaded local ML (WhisperKit transcription, SpeakerKit diarization, MLX/Gemma insights & chat, and Parakeet/FluidAudio transcription) runs in a **separate helper process**, so a CoreML/WhisperKit trap (e.g. WhisperKit's `decoderOutput.logits!` force-unwrap) kills only the helper, not the menu-bar app. The helper reserves the real stdout fd for protocol frames (`dup`) and redirects fd 1 to stderr, so a library `print()` can never corrupt the framing. Apple Speech and Apple Intelligence stay in-process (OS-managed).

**Three SPM targets:**
- **`dBriefWire`** (library, no ML deps) — the shared contract linked by both executables: the wire `Envelope`/`MLRequest`/`MLEvent`/`WireError` types, the `FrameCodec`/`FrameReader`, `LocalAIPluginProtocol`, the `Codable`/`Sendable` model structs (`TranscriptionResult`, `LocalInsightsResult`, `DiarizedTurn`, `LiveTranscriptSegment`, `LocalAIPluginState`, `WhisperRuntimeConfig`, `WhisperComputeUnits`, `OutputLanguage`), and shared utilities (`Logger` extensions, `WhisperModelInfo`, `ParakeetModelInfo`, `SystemMemory`, `LocalInsightsDecoder`).
- **`dBriefMLHost`** (executable) — links the heavy ML packages and hosts the real `WhisperKitTranscriptionService`, `MLXInsightsService`, `ParakeetTranscriptionService`, the spoken-summary TTS services `TTSService` (TTSKit/Qwen3-TTS) and `KokoroTTSService` (FluidAudio/Kokoro) — see below, the `AsyncMutex` GPU serialization, `MLOrchestrator` (the in-helper backend, formerly the in-process `LocalAIPluginService`), and a stdin/stdout `RequestLoop`. `main.swift` parses `--support-base` so the helper resolves the **same** model-cache dir as the app (its own `Bundle.main.bundleIdentifier` differs), and frees Metal buffers on SIGTERM/EOF.
- **`dBrief`** (app) — depends only on `dBriefWire`; the proxies `LocalAIPluginService` and `ParakeetTranscriptionService` forward every call over a shared `MLHostConnection`.

**Transport — `MLHostConnection` (`Services/MLHostConnection.swift`):** owns the child `Process` and its pipes, frames messages (4-byte big-endian length prefix + JSON `Envelope`), correlates replies by request `id`, demuxes `.state` events to per-`MLChannel` (`.plugin` / `.parakeet`) `AsyncStream<LocalAIPluginState>`, forwards `.token` frames to streaming `AsyncThrowingStream`s, and detects crashes via `terminationHandler` (a request in flight when the process dies throws `MLHostError.helperCrashed`). The helper is persistent, lazily spawned, and auto-relaunched on the next call after a crash. Audio is passed by file path (never over the pipe).

**Frame ordering invariant (both sides):** a request's terminal `.finished` must never overtake its result frame on the wire — if it does, `call()` resolves nothing, drops the pending entry, and leaks its continuation (permanent hang). So **neither side may dispatch frame writes/reads in per-event `Task`s**: the helper's `StdoutWriter` drains an ordered `AsyncStream` from a single task (`send` is synchronous), and `MLHostConnection` feeds stdout chunks through a single serial `AsyncStream` consumer into `ingest` (never one `Task` per chunk). This matters most for multi-frame replies (e.g. Parakeet transcription that also diarizes: result + several `.diarizing`/download `.state` events + `.finished`).

**Crash recovery:** `LocalAIPluginService.transcribeWithRetry` retries **once in safe mode** (`concurrentWorkerCount = 1`, decoder off the ANE via `.cpuAndGPU`) when the helper crashes; a second crash surfaces a clean `TranscriptionServiceError`. A normal `.error` frame (insufficient memory, audio load) propagates without retry. Because crashes are recoverable, the normal-path `concurrentWorkerCount` (8) can be raised toward WhisperKit's default of 16 with benchmarking.

The orchestrator keeps the prior behavior: **AsyncMutex** serializes GPU access; **per-op model unload** keeps an idle helper model-free; the **state stream** drives UI feedback (`idle`, `downloading(progress, stage)`, `transcribing`, `newSegments(...)`, `diarizing`, `analyzing`, `analyzingPart(index:total:)`). During map-reduce analysis `analyzingPart` drives the step's "part n of m" progress (`ProcessingStepProgress`), and `LongAnalysisNotice` tells the user that long recordings take longer to analyze (4K parts took ~1.7x as long as 10K parts on a ~55K-token recording).

**Build/packaging:** `make app` builds all executables and copies `dBriefMLHost` into `Contents/MacOS/` beside the MLX `default.metallib`. A test-only `dBriefMLHostStub` target (env `STUB_MODE=echo|crash-once|crash-always|error`) drives the connection/retry tests deterministically without real models.

### Spoken Summary — Text-to-Speech (`Services/SpokenSummaryService.swift`, `dBriefMLHost/TTSService.swift`, `dBriefMLHost/KokoroTTSService.swift`)

A **spoken-audio summary**: the AI rewrites a recording's insights into a natural-sounding narration script, which is synthesized on-device to an audio file you can play back. Triggered from the transcript viewer's **Summary** tab (a **Generate Spoken** action; once saved, it becomes **Play Spoken**), configured in **Settings → Spoken Summary**.

**Pipeline — `SpokenSummaryService`** (`@MainActor @Observable`, presented via `.sheet(item:)` from `TranscriptWindowView`): a `Phase` state machine (`idle → rewriting → preparingVoice → synthesizing → ready/failed`).
1. **Rewrite**: the active AI engine (mirroring `TranscriptChatService`'s routing — `chatFallbackEngine` substitutes for Local CLI, which can't generate) turns the summary + action items into a spoken script using `AppSettings.spokenSummarySystemPrompt` — the (editable) `spokenSummaryPrompt` with the pure `SpokenSummaryPrompt.systemPrompt(base:language:)` appending "Write the spoken briefing in <language>…" for the **spoken-summary language** (`AppSettings.spokenSummaryLanguage` = `ttsEngine.resolvedLanguage(ttsLanguage)`: the chosen `ttsLanguage` when the engine speaks it, else English). The default prompt is language-neutral; a stored copy of the old English-only default is migrated on load (`migratedSpokenSummaryPrompt`), custom prompts are kept. The prompt-editor preview (`PromptPreviewService`) composes the same way. Output is sanitized by the pure `SpokenSummaryScript.clean`.
2. **Synthesize**: `LocalAIPluginService.synthesizeSpeech(...)` writes a temp WAV via the helper; helper download/load progress surfaces as `preparingVoice(progress:)` from the `stateStream`.
3. **Save/Discard**: on Save, the WAV is transcoded to an **m4a sidecar** (`*.spokensummary.m4a`, ffmpeg AAC ~96 kbps mono, off-main) and a `SpokenSummary` script JSON sidecar is persisted via `SpokenSummaryStore`. Replaying a saved summary uses `presentSaved(...)` (no temp file, no Save). Both sidecars are swept by `RetentionCleanup` and the delete paths.

**Two TTS engines** (`AppSettings.ttsEngine`, `TTSEngine`: `.qwen3` / `.kokoro`; **Kokoro is the default**), both in the crash-isolated helper, serialized through the same `AsyncMutex`, models downloaded to `AppSupport/dBrief/LocalAIPlugin/TTS/`:
- **Kokoro** (`KokoroTTSService`) — FluidAudio's `KokoroAneManager` (ANE-resident, fast; no new dependency since FluidAudio already backs Parakeet). **37 voices in four languages** — 28 English (American/British; `KokoroVoice.afHeart`, "Heart", remains the default), 3 Spanish, 1 French, 5 Japanese; `KokoroVoice.language` derives from the id prefix and the Settings voice list is filtered to the spoken-summary language (`KokoroVoice.resolved(_:for:)` falls back to that language's default voice). The helper's `KokoroTTSService.variant(for:)` routes `ef_`/`em_` → Spanish, `ff_` → French (same ANE model as English, own text frontend) and `jf_`/`jm_` → Japanese (separate ~217 MB model; plain-text G2P since FluidAudio 0.17). Spanish/French/Japanese voice packs are fetched by FluidAudio itself on first use; Mandarin is not exposed. For English, `KokoroVoiceDownload` downloads additional ~510 KB packs from a pinned `txgsync/kokoro-82m-coreml-ane` revision, verifies SHA-256 and size, and atomically caches them in FluidAudio's English repo under `~/.cache/fluidaudio/Models/`. British packs still use the backend's US pronunciation frontend. `KokoroAneManager` caps input at ~510 phonemes and does **not** auto-chunk, so the service sentence-greedy chunks (measured via `engine.phonemes(for:)`, word-level fallback) and concatenates per-chunk samples with a ~100 ms gap. No style control; Kokoro's language comes from the voice id.
- **Qwen3-TTS** (`TTSService`, TTSKit) — macOS-only, multilingual. Picks a model size (`TTSModelSize` `.small`/`.large` — only 1.7B follows the voice-style `instruction`), a `TTSVoice` (9 speakers), speaks any of the 10 `TTSLanguage`s (from the shared spoken-summary language), and an editable calm-delivery `ttsDeliveryInstruction`.

**Wire path**: `MLRequest.synthesizeSpeech(text:outputPath:voice:language:instruction:model:engine:)` → `RequestRouter` → `MLOrchestrator.synthesizeSpeech` (routes to the Kokoro or Qwen3 service by `engine`, unloading the other) → `MLEvent.speechResult(SpeechSynthesisResult)`. App proxy: `LocalAIPluginService.synthesizeSpeech(...)`. All voice/engine enums live in `dBriefWire/SpeechSynthesisResult.swift`; `AppSettings.ttsSynthesisParams` bundles the resolved params. `DownloadStage` has `.ttsModel` / `.ttsModelLoading` for progress.

**Voice preview** (`Services/VoicePreviewPlayer.swift`, `@Observable`): the **Preview voice** button in Settings synthesizes a short `TTSLanguage.sampleText` and plays it through a private `AudioPlayer` (no transcode, no touching shared playback), with inline preparing/synthesizing/playing/failed state.

### Call Detection (`Services/CallDetectionService.swift`)

`CallDetectionService` monitors for known meeting apps (`knownCallApps`: Zoom, Teams classic/new, Slack, Webex, FaceTime, Google Meet) via `NSWorkspace` notifications and microphone activity via CoreAudio `kAudioDevicePropertyDeviceIsRunningSomewhere`. Can auto-start recording (`autoRecordCalls`) or show a popup prompt (`CallDetectedOverlayController`). The prompt can **auto-dismiss** after `AppSettings.autoDismissCallPromptSeconds` (0 = never; the timer is scheduled in `CallDetectedOverlayController.show()` and cancelled in `hide()`, so any user interaction cancels it). Per-app enable/disable via `AppSettings.disabledCallApps`. Configured in **Settings → General → Call Detection**.

**Stop recording when a call ends**: the mirror of auto-start. `AppSettings.stopRecordingOnCallEnd` (`CallEndAction`: `.off` / `.prompt` / `.autoStop`, default `.prompt`) and `callEndScope` (`CallEndScope`: `.callInitiatedOnly` (default) / `.anyActiveRecording`) drive it, configured in **Settings → General → Call Detection** ("When a call ends" / "Apply to"). The outcome is the pure, unit-tested `CallEndDecision.decide(action:scope:isCapturing:endedBundleId:initiatorBundleId:alreadyPrompting:)` (`Services/CallEndDecision.swift`, `CallEndDecisionTests`, mirrors `MicReconfigurePlanner`): it returns `.ignore` / `.stop` / `.prompt` — under `.callInitiatedOnly` it acts only when the ended app is the one that started the recording (`AppState.callRecordingBundleId`), under `.anyActiveRecording` it acts for any active capture. `.prompt` shows the `CallEndedPopup` (same `CallDetectedOverlayController` panel machinery + auto-dismiss as the detect prompt); `.autoStop` calls `RecordingManager.stopRecording()`.

- **Detecting the *end* signal** (`Services/CallAudioActivityMonitor.swift`, macOS 14.2+): the aggregate `DeviceIsRunningSomewhere` can't detect a call ending because dBrief holds the mic open for the whole recording, so it never goes idle mid-recording. Instead the monitor watches each call app's **per-process** mic input (`kAudioProcessPropertyIsRunningInput`) — which reflects the meeting app alone. When Zoom/Teams/etc. stops using the mic (leaving a meeting even while the app stays open), its process flag flips to `false`. A **4 s grace** debounces brief drops (mute, device switch) so only a sustained input-off fires the end path. **The CoreAudio change-listener is unreliable** — for some apps (observed: Zoom releasing the mic on leaving a meeting) it never delivers a callback — so a **2 s main-queue poll** re-reads each monitored process's input state as the reliable signal (`reportInputState` dedupes, so poll and listener never double-fire). On macOS < 14.2 there is no per-process signal, so call-end is detected only when the call app **fully quits** (`handleAppEvent` termination path, gated `#unavailable(macOS 14.2)` to avoid double-firing on newer OSes).

### Calendar Integration (`Services/CalendarService.swift`, `OutlookCalendarService.swift`)

On recording **stop**, `RecordingManager.lookupCalendarCandidates(for:)` looks up the matching calendar event(s) to pre-fill the meeting title, participants (used as diarization speaker names), and agenda context for AI prompts. The lookup happens at stop (not start) because only then is the true recording span `[date, date+duration]` known, which the span-aware matcher needs; it runs detached so the post-recording sheet appears immediately and the ranked candidates + best match populate reactively via `@Observable`. Two sources behind `AppSettings.calendarSource` (`CalendarSource`: `.disabled`/`.iCal`/`.outlook`):
- **iCal** — `CalendarService.findCandidates(recordingStart:recordingEnd:)` via EventKit (`EKEventStore`), needs Calendar permission
- **Outlook** — `OutlookCalendarService.findCandidates(recordingStart:recordingEnd:)` via Microsoft Graph; auth through `MicrosoftAuthService` (OAuth2, Keychain-stored). The Outlook option only appears when `MicrosoftAuthService.isConfigured` (a real Azure client ID is compiled in, not the placeholder).

Both search a ±2h window and rank candidates via the pure, unit-tested `CalendarMatcher.rankedMatches(...)`: each candidate is scored by intersection-over-union of its window vs. the recording span, `+0.10` if it was active at recording start, `+0.15` if it has attendees, and `×0.10` to sink all-day blocks — so a day-long personal block never wins over the short meeting it overlaps. `selectBestMatch(...)` returns the top. `Recording.calendarCandidates` holds the ranked list; `PostRecordingSheet` shows a **"Meeting" override picker** (with a "None" option) so the user can correct or clear the auto-pick (guarded auto-fill via `applyCalendarEvent` never clobbers typed input; an explicit pick via `selectCalendarEvent` overwrites title + participants). `AppSettings.effectiveCalendarSource` coerces `.outlook` → `.disabled` when Outlook isn't configured, so a stale selection never renders sign-in UI. Configured in **Settings → General → Calendar**.

### Speaker Diarization (`Services/WhisperKitTranscriptionService.swift`)

Optional SpeakerKit integration (Pyannote v4 models) for identifying who said what:

- Enabled via `AppSettings.diarizationEnabled` toggle in Settings → Recording
- Runs sequentially after WhisperKit transcription (not parallel — both compete for GPU/ANE)
- `SpeakerKit(PyannoteConfig)` initialized on-demand, models downloaded to `AppSupport/dBrief/LocalAIPlugin/SpeakerKit/`
- Speakers are overlaid **additively**: the full WhisperKit transcript is mapped to `dBriefWire.TranscriptionResult` (every segment kept), `diarResult.segments` is converted to `[DiarizedTurn]`, and `SpeakerMerge.mergePreservingSegments(_:turns:)` attaches speakers by time overlap. This replaced `SpeakerKit.addSpeakerInfo(strategy: .subsegment)`, which **silently dropped any segment lacking word timestamps** — a custom-vocabulary `initialPrompt` routinely makes WhisperKit omit word timings, so diarization + a vocabulary prompt used to lose most of the transcript. `mergePreservingSegments` never rebuilds segment text from words (unlike `SpeakerMerge.merge`), so partial/sparse word timing can't truncate text; the trade-off is one speaker per segment (plus per-word labels) instead of within-segment splitting.
- Speaker IDs ("Speaker 1", "Speaker 2") stored in `TranscriptionResult.Segment.speaker` and `Word.speaker`
- **Participant mapping**: Users enter comma-separated names in `PostRecordingSheet`; `RichTranscriptBuilder.build(from:participants:)` maps names to speakers by ordinal (first speaker = first name)
- **Post-hoc speaker assignment**: Clicking a speaker label on a turn card in `TranscriptWindowView` opens a selection-based `Menu` (`speakerMenuContent(turn:isMe:)`) split into three actions, all applied by the pure, unit-tested `SpeakerReassignment` (`Services/SpeakerReassignment.swift`) and persisted via `TranscriptStore` (`.richtranscript.json` sidecar). Candidate names come from `SpeakerReassignment.candidates(...)` (other speakers + `recording.participants` + calendar attendees), computed lazily inside the menu:
  - **Rename to ▸** — a submenu of selectable names (known people + other speakers); picking one calls `SpeakerReassignment.rename(_:speakerId:to:)`, which edits the speaker's `SpeakerLabel.displayName`, keeping its `speakerId` and all segments. If the chosen name (case-insensitively) already belongs to **another** speaker, the two **swap** display names — the fix for diarization mixing up who's who; no speaker is merged or lost. A **Custom name…** item opens the small `SpeakerRenamePopover` text field (the only-when-needed typing fallback). When there are no candidate names, the menu shows a direct **Rename…** item instead of the submenu.
  - **Move this turn to ▸** (and, when the speaker spans more than this turn, **Move all "<name>" to ▸**) — submenus of the *other* existing speakers; picking one calls `SpeakerReassignment.apply(.existing(...))` with scope `.theseSegments` / `.allOfSpeaker`. `apply` rewrites `RichSegment.speakerId` over the chosen segment ids, drops orphaned `SpeakerLabel`s (moving *all* of a speaker's segments into another thus merges them), and transfers `meSpeakerId` if its speaker is fully merged away.
  - **This is me / Clear "This is me"** — unchanged (`setMeSpeaker`).
- Display names resolved through `RichTranscript.speakerLabels` in both transcript viewer badges and markdown output

**Parakeet diarization** (same `diarizationEnabled` toggle): Parakeet has no built-in speaker support, so `MLOrchestrator.parakeetTranscribe(…, diarize:)` runs the engine-agnostic standalone pass `WhisperKitTranscriptionService.diarize(fileURL:) -> [DiarizedTurn]` (SpeakerKit, reused, after unloading the Parakeet model to free memory), then merges speakers onto Parakeet's word-level segments via the pure `SpeakerMerge.merge(_:turns:)` helper in `dBriefWire` — assigning each word its best-overlapping turn and regrouping consecutive same-speaker words into segments. The diarization flag rides on `MLRequest.parakeetTranscribe(path:modelVariant:diarize:)`. This makes Parakeet diarization full-pipeline (rich transcript, participant mapping, markdown, integrations), unlike the app-side post-hoc `SpeakerAssigner` re-diarize in the transcript window. `SpeakerMerge` is the wire-type analogue of `SpeakerAssigner` (which still operates on `RichTranscript`).

**Cross-part speaker reconciliation** (`Services/SegmentSpeakerReconciler.swift`): when a long recording is auto-segmented into 30-minute parts, each part is diarized independently, so "Speaker 1" in part 1 is a different cluster than "Speaker 1" in part 2. `SegmentSpeakerReconciler.reconcile(_ parts:)` (pure, unit-tested) unifies them into one global speaker space: it greedily one-to-one matches each part's speakers against the running mean voiceprint of the existing global speakers by cosine similarity (`matchThreshold = 0.5` — well above the ~0.28 cross-speaker baseline, since all parts share one mic/session), and any unmatched local speaker (no embedding, below threshold, or lost contention) becomes a **new** global "Speaker N" rather than risk a wrong merge. The `Result` carries per-part `remaps` (local→global id), one mean `speakerEmbeddings` vector per global speaker, and the global `speakerCount`. `RecordingManager.mergeSegmentTranscriptions(_:)` applies each remap to segment + word speaker ids, offsets timestamps, and forwards the reconciled speakers, merged embeddings, and count downstream (so voice-library matching and AI analysis see one consistent set of people).

**Confirm-first speaker review** (Phase 3b): `AppSettings.speakerIdMode` (`SpeakerIdMode.optimistic` (default) | `.confirmFirst`, picker in **Settings → Transcription**, shown only when `diarizationEnabled`) controls whether diarized speaker identities are confirmed before the rest of the pipeline runs. In `.optimistic` mode, recognized voices are auto-labelled and processing continues straight through. In `.confirmFirst` mode the pipeline **holds** after diarization and presents a review window so the user can fix names before AI analysis. The hold is gated by the pure `SpeakerReviewGate.shouldHold(mode:speakerCount:libraryCount:)` — only holds when `.confirmFirst` and (≥2 speakers or a non-empty voice library), so a solo memo with no library still runs through. Supporting pure helpers: `SpeakerReviewCandidates.topMatches(...)` ranks library people by max cosine for the per-speaker suggestion chips; `SpeakerSnippet.representative(...)` picks each speaker's longest turn (capped ~6 s) for an audition snippet.

- **Hold state**: `SpeakerReviewSession` (`Models/SpeakerReviewSession.swift`) captures the paused pipeline — `origin` (`.pipeline` for a fresh transcription, `.rediarize` for a re-diarize from the open viewer), the recording, master audio URL, the per-speaker `items` (proposed name, match `Reason`, cluster embedding, snippet range), the captured processing toggles, and pre-measured transcription perf. It is held on `AppState.pendingSpeakerReview`; the viewer reload signal is `AppState.speakerReviewCommit` (recordingID + token + `offerReanalysis`).
- **Window**: `SpeakerReviewWindowController` (singleton AppKit window, transparent titlebar / glass look matching the mini-player; flips activation policy to `.regular` for keyboard input when no dock icon) hosts the SwiftUI `SpeakerReviewView` — one card per speaker with an editable name, snippet play/stop (`AudioPlayer.playRange(...)`), and up to two suggestion chips.
- **Resume**: `RecordingManager.finishReview(confirmed:)` applies the edits via `SpeakerReassignment.rename(...)`, enrolls confirmed voiceprints, persists the transcript, then `resumeAfterReview` either runs analysis+export (`.pipeline`) or signals the viewer to reload (`.rediarize`); `cancelReview()` keeps the resolver's original names and resumes. A red-button close is treated as cancel. The re-diarize-from-viewer entry is `presentReDiarizeReview(...)`, which overlays fresh turns via `SpeakerAssigner`, checks the same gate, and either holds (returns `true`) or lets the caller commit silently (`false`).

**Important**: WhisperKit's `TranscriptionResult` class conflicts with dBrief's `TranscriptionResult` struct (same name, different modules). The `WhisperKit` module name also collides with the `WhisperKit` class. As a result, diarization code that uses both types must be inlined within `transcribe()` where `wkResults` type is inferred — it cannot be extracted into separate functions with explicit type annotations. Use `dBrief.TranscriptionResult` to qualify our type.

### Voice Library (Speaker Recognition)

A persistent, on-device voice library lets diarized speakers be **auto-recognized** across recordings (not just diarized within one). Stored as a single `library.json` under `~/Library/Application Support/com.dbrief.app/VoiceLibrary/` — never per-recording, never uploaded, and outside the folders `RetentionCleanup` touches. Managed in **Settings → Voice Library**.

- **Embedding pass** (`Sources/dBriefMLHost/SpeakerEmbeddingExtractor.swift`) — after diarization, the helper extracts one 256-dim voiceprint per qualifying speaker cluster via FluidAudio's WeSpeaker model (`modelTag = "fluidaudio-wespeaker-256"`, models cached alongside the other FluidAudio models), runs inside the GPU mutex, best-effort (`[:]` on any failure). Carried back on `dBriefWire.TranscriptionResult.speakerEmbeddings` (`[speakerId: [Float]]?`) via the wire `MLEvent.diarizeWithEmbeddingsResult(turns:embeddings:)`.
- **Model** (`Models/VoiceLibrary.swift`) — `VoiceLibrary` → `[KnownPerson]` (stable UUID `id` that survives rename, display `name`, `[Voiceprint]`); `Voiceprint` is a 256-dim L2-normalized `embedding` + `model` tag + `capturedAt`.
- **Store** (`Services/VoiceLibraryStore.swift`) — `actor`, atomic-write JSON, mirrors `ModelPerformanceStore`. CRUD: `upsert`, `rename` (returns `RenameOutcome.collision` so the UI offers a merge), `merge`, `delete`. Display sorting is the pure `VoiceLibraryDisplay`.
- **Pure helpers (no IO/ML, unit-tested):** `VoiceMatch.cosineSimilarity`; `VoiceIdentityResolver.resolve(clusterEmbeddings:library:roster:)` matches each speaker cluster to a known person by max cosine, gated by a non-empty **roster** (participants + calendar attendees, the same set `AnalysisRoster` feeds to AI prompts), a **margin** over the runner-up, and one-person-per-cluster **contention** (defaults `minConfidence 0.55`, `margin 0.07`), returning a `Decision` with a `Reason`; `VoiceEnrollment.enrollable(...)` selects speakers that have a real user-assigned name **and** an embedding, and `isDuplicate(...)` keeps a person's prints diverse.
- **Wiring** (`RecordingManager`) — after diarization the resolver auto-labels recognized speakers against the loaded library; once names are finalized (via `PostRecordingSheet`/post-hoc reassignment), named speakers' voiceprints are enrolled via `VoiceLibraryStore.upsert`. Requires `diarizationEnabled`; no embeddings ⇒ speakers left unnamed (no ordinal guess when a library exists).

### Live Transcript

`AppState.liveTranscriptSegments` (+ `liveVolatileMic`/`liveVolatileSystem`/`liveStatusMessage`) drives a real-time transcript view that's filled in two phases — while recording (optional Apple Speech preview) and while WhisperKit transcribes the finished file. Both render inside `TranscriptDetailView`'s **live mode** (there is no standalone live window); the in-progress recording is pinned at the top of `TranscriptBrowserView`'s sidebar ("In Progress"), and the **"Live Transcript"** button in `TranscriptionProgressView` opens the transcript window (`id: "transcript"`) with it selected.

**Real-time, during recording — `LiveTranscriptionService` (`Services/LiveTranscriptionService.swift`)**: optional (`AppSettings.liveTranscriptionEnabled`, default off; **Settings → Transcription → Live Transcription**), separate from the authoritative transcript still produced by the chosen engine at stop. An `actor` running two concurrent in-process Apple Speech channels — mic ("You") and system audio ("Participant"); macOS 26+ uses the streaming `SpeechAnalyzer`/`SpeechTranscriber` (volatile + finalized, input converter rebuilt on source-format change), macOS 14–25 falls back to `SFSpeechAudioBufferRecognitionRequest`. On-device only. Each channel transcribes a **single locale** (`AppSettings.effectiveTranscriptionLanguage`, or the system locale when empty) — Apple's streaming recognizer has no language auto-detect or code-switching, so mixed-language meetings get an accurate result only from a multilingual *post-recording* engine (Parakeet v3 / Whisper), not the live preview.
- **Live audio feed**: `AudioCaptureManager.makeLiveAudioStreams()` (called *before* `startRecording` so the tap handlers capture the sinks) returns mic + system `AsyncStream<LiveAudioBuffer>`. Tap handlers deep-copy each buffer into a `LiveAudioBuffer` (an `@unchecked Sendable` wrapper, so the stream crosses the main-actor → transcription-actor boundary without `sending` gymnastics) in addition to writing the CAF tracks; the converting hot-swap handler feeds the live sink too, so live transcription survives a mid-recording mic device switch. Streams use `.bufferingNewest` (bounded — a lossy preview, not unbounded RAM) and are finished by `stopRecording`.
- **Orchestration**: `RecordingManager.startLiveTranscription(streams:)` starts the service (gating each channel on its permission); finalized segments → `liveTranscriptSegments` (ordered by the pure, end-anchored `LiveSegmentMerge.insert`), volatile text → `liveVolatile*`, status → `liveStatusMessage` ("Preparing language…" during a first-run language-asset download). `stopLiveTranscription` cancels it on stop/reset.
- Pure, OS-independent, unit-tested helpers in `dBriefWire`: `AppleSpeechResultMapper.liveSegments` (chunk → speaker-tagged `LiveTranscriptSegment`) and `LiveSegmentMerge` (`LiveTranscriptMappingTests`).

**Progressive, during WhisperKit transcription**: WhisperKit's `segmentDiscoveryCallback` fires each time a ~30-second audio chunk is decoded; segments convert to `LiveTranscriptSegment` and are pushed via `LocalAIPluginState.newSegments(...)`, which `RecordingManager` appends to the same `liveTranscriptSegments` (cleared on each new transcription).

### Watched Folders (`Services/WatchedFolderService.swift`, `Services/WatchedFolderScanner.swift`)

A drop-in transcription queue: audio files dropped into a watched folder are auto-transcribed/analyzed/exported via the normal pipeline, no recording needed. Off by default (`AppSettings.watchedFoldersEnabled`).

- **`WatchedFolderScanner`** (pure, unit-tested) — `audioFiles(in:)` enumerates a folder non-recursively for `audioExtensions`; `newlyStableFiles(current:previous:processed:)` returns files that are **size-stable across two consecutive scans** (so a file still being copied isn't grabbed) and not already processed. No state, fully testable without disk.
- **`WatchedFolderService`** (`@MainActor @Observable`) — a lightweight ~4 s polling loop (not FSEvents) that re-reads live settings each cycle, so toggling folders/the master switch needs no restart. Resolves each `WatchedFolder` bookmark and enumerates off-main via `Task.detached`. **Seed-on-first-encounter**: a folder's pre-existing files are recorded as already-processed the first time it's seen, so adding a folder only processes files dropped in *afterwards* (never an existing library at once). Processed paths + known folders persist in `UserDefaults` (bounded to 5000). Serial, and defers to any active recording/processing via `RecordingManager.isIdle`. Started from `AppContext.ensureReady()`; self-gates when disabled/empty.
- **`WatchedFolder`** (`Models/WatchedFolder.swift`) — `Codable`/`Sendable` struct holding a security-scoped bookmark, display path, and `isEnabled`; persisted as JSON in `AppSettings.watchedFolders`.
- **`RecordingManager.processWatchedFile(_:)`** — headless entry: copies the source to a temp file and sets `importSourceURL` so the finalizer relocates the **copy** into the recordings folder (original left untouched, result lands in History), then runs `processRecording` with the global `autoTranscribe/autoSummary/autoActionItems/autoTags` prefs.
- Configured in **Settings → Watched Folders** (`SettingsWatchedFoldersTab`): master toggle, folder list (add via `NSOpenPanel`, per-folder enable, remove), and a "Notify when a new file is detected" option (completion notifications fire regardless via the normal pipeline).

### Transcript Chat (`Services/TranscriptChatService.swift`)

`TranscriptChatService` (`@MainActor @Observable`) provides conversational Q&A over a recording:

- Holds a `[ChatMessage]` array and an `isStreaming` flag
- Routes to Apple Intelligence, MLX (streaming), or remote endpoint based on `AppSettings.aiEngine`
- **Transcript format**: the model sees one line per turn, `[hh:mm:ss] Name: text` (`ChatTranscript.format` in `dBriefWire`), so it can cite timestamps and tell speakers apart.
- **Engine profiles** (`ChatEngineProfile`, `dBriefWire/ChatEngineProfile.swift`): per-engine token budgets (`fullTranscriptTokens`, `excerptTokens`, `overviewTokens`, `historyTokens`, `scanPartTokens`, `scanFindingsTokens`, `reusesSession`). **Gemma is fixed** (24K full-transcript, 4K excerpts, 8K overview, warm session); **Apple Intelligence is derived from the model's `contextSize`** (`ChatEngineProfile.appleIntelligence(contextSize:)`: 55% full transcript, 30% excerpts, 25% overview, 10% history, so ~35% stays free for the answer), which scales automatically when a later OS grows the window. Gemma's 4K excerpts and Apple's 30/25 split were chosen by measurement (see "Long-transcript chat eval" below). Token counts are an estimate (`estimateTokens`, 3 chars per token) except the Apple full-transcript check, which uses the exact `SystemLanguageModel.tokenCount` on macOS 26.4+.
- **Three modes** (`ChatContextPlanner.mode`): `fullTranscript` when the transcript fits the profile (the whole text goes in the system prompt, unchanged behaviour); `overviewAndRetrieval` for a long finished recording with saved part notes or summary (a whole-meeting overview from `ChatOverview.make` - the sidecar part notes when they fit, else summary + action items, else the summary cut at a sentence - plus hybrid excerpts for the question); `retrievalOnly` when there is no overview. Retrieval is `TranscriptRetrieval.hybridExcerpts`: the top 30 BM25 windows fused (RRF) with the top 30 cosine windows, assembled with one neighbour window per hit within `excerptTokens`; with no vectors it is BM25 only. Windows are ~350 tokens with one turn of overlap.
- **Retrieval index** (`<base>.chatindex.json`, `ChatIndex`): `intfloat/multilingual-e5-small` (~480 MB, downloaded on demand, `EmbeddingPrompt.current`) runs in the ML helper (`EmbeddingService`), is **shared by both engines**, and is built lazily at first long-mode question, then cached next to the audio. It was chosen over EmbeddingGemma-300M by measurement: e5 put all three planted needles at fused rank 1, while EmbeddingGemma's MLX backbone uses a causal attention mask, which hurts it as a retrieval encoder. When embedding fails, that question uses keyword-only (BM25) retrieval and the next one retries the build (a BM25-only index is never saved); with no index location (or no ML helper) there is no retrieval, only the overview. The index is written through `RecordingResultMutation.withWrite` with the session's validity, like `chat.json`; a refused write is logged and the in-memory index still used. The sidecar records the model id and a content hash of the windows, so a model or transcript change rebuilds it.
- **Gemma warm session** (`GemmaChatSessions`, `dBriefMLHost`), used in **both full and long mode**: the system prompt (full transcript, or instructions + overview) is stable, so one `ChatSession` is kept **warm** across turns and each follow-up prefills only its new question (plus excerpts in long mode); idle for 5 minutes (or any other model operation) drops it. The KV cache **growth** is capped at 32K tokens past the session's initial prefill, after which the session is rebuilt from history. Each turn's excerpts are sent as `retrievedContext` on the user turn, never stored in the system prompt.
- **Apple long mode** (`AppleChatBackend`, `Services/AppleChatBackend.swift`): a **fresh `LanguageModelSession` per question** (the context window is too small to carry a conversation), with `ChatContextPlanner.freshSessionPrompt` = compact history (`compactHistory`, newest Q&A pairs within `historyTokens`) + excerpts + question. One **overflow retry**: on a context-overflow error `AppleChatAttempt.next` retries once with `profile.shrunk()` (¾ of the full-transcript budget, so a transcript that only just fit can fall into long mode; half the excerpts and overview; no history); a second overflow on a finished recording shows an error pointing to "Check the whole recording" with that button under it (`offerScan`). Turn-less *live* chat has nothing to retrieve from (and no scan), so a long live transcript uses `AppleChatContext.recentTail` (the newest whole lines that fit), footed "Answered from the most recent part of this live recording." (`ChatCoverage.recentPart`).
- **"Check the whole recording"** (`scanWholeRecording(for:)`, button under a long-mode answer or an Apple overflow error): an opt-in exhaustive pass for questions retrieval can miss ("list every ..."). The transcript is split into parts of `scanPartTokens` (`TranscriptChunkPlanner`), each part is asked for its evidence (`scanPartPrompt`, reply `NONE` when nothing is relevant), and the answer is written from the non-NONE findings (`scanFinalPrompts`, several groups joined under "Part a-b" headings when Apple's window can't hold them all; nothing is ever silently clipped). Gemma uses the one-shot `chatStream` (never the warm session, which it drops); Apple retries an overflowing part as halves and counts a refusal as "no findings" for that part. Measured on Gemma: 8 parts, ~7.6 minutes for a 75K-token recording (~6 ms/token), every planted fact found; the button text is concrete for Gemma ("about N minutes", `ChatScanEstimate`) and "takes a few minutes" for Apple Intelligence.
- Builds the system prompt from a **`transcriptProvider: @MainActor () -> String` closure** (not a fixed string) read at each `send()`, plus speaker labels — so the chat can run against a *live, growing* transcript during recording (the provider reads `AppState.liveTranscriptSegments` + volatile lines). A `transcriptText:` convenience init covers the fixed finished-recording case.
- `rebind(turns:transcriptText:speakerLabels:insightsURL:indexURL:)` re-points an existing session at a changed transcript while keeping its messages, dropping the index, long-mode prompt and cached insights (no-op when nothing the model sees changed). `TranscriptWindowView.setTranscript` calls it on every transcript mutation (rename, moved turns, speaker-review reload), and a finished live recording rebinds its carried-over Q&A (an empty live chat is dropped instead); all build the content with `ChatTranscriptContent.make`, the same builder a new session uses.
- **Persistence**: `TranscriptChatStore` caches one live session per recording for the app run (keyed by audio file URL); on top of that, chat is **persisted to disk** as a `<base>.chat.json` sidecar. `ChatStore` (actor, mirrors `InsightsStore`) loads/saves a `Codable` `ChatHistory` (`version`, `[ChatMessage]`, optional `engine`). A finished recording's session calls `enablePersistence(store:url:)` + `startLoadingPersisted()` when the chat panel opens (so history survives an app restart); `send()` `await`s that load before appending so a fast typist can't overwrite the saved file, and triggers a debounced (~500 ms) `scheduleSave()`. `clearMessages()` deletes the sidecar. When a live recording finishes, the carried-over chat gains persistence and flushes via `persistNow()` (`recording.chatSidecarURL` only resolves once the audio is finalized). On quit, `AppDelegate.applicationShouldTerminate` calls `TranscriptChatStore.flushAll()` → `flushPendingSave()` on each session before `_exit(0)`, so an exchange sent inside the debounce window isn't lost (a per-session `hasUnsavedChanges` flag skips redundant writes). The `.chat.json` and `.chatindex.json` sidecars are included in `RetentionCleanup`'s transcript sweep, in both delete paths (`TranscriptWindowView.deleteRecording`, `RecordingHistoryView.deleteItem`) and in the reprocessing manifest.
- `TranscriptChatView` renders the conversation with a command-palette layout and glass styling. In the finished-recording viewer it's a full-pane mode swap; during **live mode** it opens as a right-hand side panel (`TranscriptDetailView.liveChatPanel`) so the growing transcript stays visible.

**Long-transcript chat eval** (dev tooling, results in the gitignored `docs/diagnostics/chat-eval.jsonl`, raw reports in `~/gemma-eval/results/`): `scripts/chat-eval.py <transcript> --mode long` drives the helper's `--eval-chat` (`GemmaEval.runChat`: `--mode full|long|scan`, `--dump-index` guarded to `~/gemma-eval/`) with four planted questions (three facts plus one exhaustive "list every action item"); `--engine apple` then runs the env-gated `AppleChatEvalTests` (`DBRIEF_APPLE_EVAL=1`, skipped in a normal `swift test`) over the dumped index and scores the answers with the same probes. Never print answers; the dump holds private text and is deleted after use. Numbers on a 75K-token (L) recording: Gemma full mode answers Q1-Q3 but misses the exhaustive Q4 (first question ~194 s, follow-ups <1 s); Gemma long mode (4K excerpts) hits all four with a first question ~38 s and follow-ups ~11-21 s; Apple Intelligence long mode (30/25 split) hits all four in ~2-5 s per question, against 0 of 4 for the old head+tail truncation. `DBRIEF_EVAL_EXCERPT_TOKENS` overrides Gemma's excerpt budget in the eval only.

The **"Low RAM" processing tag** (`TranscriptionProgressView`) now renders only while a step is in progress **and** `appState.memoryPressureLevel == .critical` — previously it fired on `.warning` too, which macOS raises routinely on 16 GB Macs, so the tag was a false alarm. ## Key Patterns

- All UI and state classes are `@MainActor @Observable`. Services that do async work are `actor`-isolated (`TranscriptionService`, `AIService`, `LocalAIPluginService`, `MLXInsightsService`, `WhisperKitTranscriptionService`, `IntegrationDispatchService`, `RecordingFinalizer`).
- Logging uses centralized `Logger` extensions defined in `Logger+Extensions.swift` (e.g. `Logger.audio`, `Logger.recording`, `Logger.ai`). New files should use these static loggers rather than creating ad-hoc `Logger(subsystem:category:)` instances.
- Models are `Sendable` structs/enums for safe cross-isolation passing.
- Settings persistence uses `UserDefaults` with `didSet` observers on each property. Folder URLs use security-scoped bookmarks. Sensitive tokens use `KeychainHelper`.
- The app links system frameworks via SPM linker settings (not Xcode build settings).
- Audio tap handlers use `nonisolated static` factory methods to avoid `@MainActor` isolation on the real-time audio thread.
- WhisperKit, SpeakerKit, and MLX models are downloaded on-demand to `~/Library/Application Support/dBrief/LocalAIPlugin/` and can be purged from settings.
- **WhisperKit type collision**: The `WhisperKit` module and `WhisperKit` class share the same name, making `WhisperKit.TranscriptionResult` ambiguous. Use `dBrief.TranscriptionResult` to refer to our type; keep WhisperKit result types inferred (never name them explicitly in function signatures). Import with `@preconcurrency import WhisperKit` for Sendable suppression.
- Metal GPU support is auto-detected; the `make app` target copies `.metallib` files from the build or downloads prebuilt ones from the MLX releases.
